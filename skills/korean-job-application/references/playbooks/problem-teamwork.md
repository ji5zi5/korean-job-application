# 문제해결과 협업 문항 작법

공개 사례의 `합격 자소서`는 플랫폼 라벨일 뿐 고용주 검증, 지원자 사실 확인, 합격 원인 증명이 아니다. 원문 답변·지원자 프로필을 복사하지 않고, 실제 문항의 요구와 짧은 관찰만 집필 판단에 쓴다.

확인된 경험 사실, 회사/공고 사실, 미래 제안은 분리한다. 필요한 사실이 모두 있으면 바로 작성하고, 일부만 있으면 새 행동·수치·감정을 만들지 않는 `작업용 초안 — 제출 전 확인 필요`를 낸다.

## Q03. 문제해결·개선

### 실제 질문 연결

- [BH02 — SK텔레콤 HRD](https://linkareer.com/cover-letter/20360): 실제 문항은 정보 수집과 문제 해결을 요구한다. 회원 설문으로 선호를 나누고, 상대방 이익을 포함한 제휴안을 만든 흐름이 관찰되지만 설문→제휴 결과의 인과 범위는 과장할 수 없다.
- [BH03 — SK텔링크 HR 운영·지원](https://linkareer.com/cover-letter/31338): 실제 문항은 문제해결·개선을 요구한다. 진로설명회 개선에서 수요 설문을 반대 의견 설득의 근거로 사용한 사례이며, 방문자 증가와 개인 기여 범위는 별도 확인 대상이다.
- [IT04 — 카카오뱅크 Developer](https://linkareer.com/cover-letter/33162): 실제 문항은 난제·해결을 요구한다. 여러 프로젝트를 나열하면 개인 결정과 결과가 분산될 수 있어 한 사건의 제약·선택·확인 결과를 우선해야 한다는 비교 재료다.
- [ER05](../cases/expert-reviewed.md#er05--한국전력공사)는 5/5 평가에서 문제 발견·해결 문항의 하위 요구 대응을 호평받았다. [ER04](../cases/expert-reviewed.md#er04--카카오)는 자유·경력 문항 안의 기술 오류 대응을 비교할 자료다(전체 4/5). 원문의 문항 유형과 대목의 주제는 구분한다.

### 의도와 하위 요구

독자는 불편·오류·목표 미달을 어떻게 파악했는지, 원인을 어떤 근거로 좁혔는지, 대안 중 무엇을 왜 실행했는지, 확인된 변화와 한계가 무엇인지 본다. 단순히 열심히 했거나 결과가 좋았다는 답은 문제해결의 근거가 아니다.

### 적합한 소재

- 반복 오류·지연·낮은 참여·고객 불편처럼 문제와 기준이 확인되는 경험.
- 관찰 기록, 설문, 비교, 검토 결과 등 원인을 좁힌 근거와 실제로 바꾼 절차.
- 해결이 완전하지 않았더라도 조정 후 확인한 산출물·반응·남은 제약.

문제가 본인의 권한 밖이었으면 해결했다고 넓히지 않는다. 제안·조율·확인만 했다면 그 범위로 쓴다.

### 전개 선택지

1. **진단 중심:** 문제 신호 → 원인 확인 근거 → 선택한 조치 → 확인 결과·한계.
2. **개선 반복 중심:** 첫 시도의 부족 → 피드백/데이터 → 수정한 방법 → 다음 기준.

문제가 개인의 실수에서 출발했으면 실패·회복(Q06)과 겹칠 수 있다. 문항이 개선 방법을 묻는다면 진단과 조치에, 실패의 책임과 이후 습관을 묻는다면 Q06에 중심을 둔다.

### 작성·수정 절차

1. 문제를 “무엇이, 누구에게, 어떤 기준에서” 문제였는지 한 문장으로 적고, 추정 원인과 확인된 원인을 구분한다.
2. 대안·제약·내 책임 범위를 써서 선택 이유를 고정한다.
3. 결과는 수치면 기간·비교 기준·기여 범위를, 수치가 없으면 산출물·피드백·관찰된 변화를 쓴다.
4. 충분하면 완성 초안을 만든다. 원인이나 결과가 없으면 `[확인 필요: 원인 판단의 근거/조치 뒤 확인된 변화]`를 둔 부분 초안으로 멈춘다. “개선했다”만 있는 문장은 관찰→조치→확인 순으로 수리한다.

### 피할 선택과 짧은 예시

발생한 모든 문제를 나열하기, 동시 발생한 결과를 내 행동의 유일한 효과로 쓰기, 미래 제안을 완료 성과로 쓰기는 피한다.

`[가상 예시] 신청 누락이 접수 직전에 드러나는 기록을 확인해 항목별 확인 순서를 제안했습니다. 다음 접수에서는 담당자와 같은 표로 누락 여부를 확인했습니다.`

## Q04. 협업

### 실제 질문 연결

- [IT04 — 카카오뱅크 Developer](https://linkareer.com/cover-letter/33162): 실제 문항은 협업을 요구한다. 서로 다른 담당 영역에서 생긴 협업 문제를 정기 공유 방식으로 바꾼 관찰은, 공동 결과보다 공유·조율 방식과 개인 선택을 보여 주어야 함을 말한다.
- [SS01 — E1 국내영업](https://linkareer.com/cover-letter/36234): 실제 협업 문항에서 팀 이견을 일정과 리소스의 시각화로 다룬다. 이는 공동 목표·의사결정·중재 역할을 구체화한 재료지만, 성과 수치와 회사 표현은 별도 근거가 필요하다.
- [FI02 — 신한은행 일반직](https://linkareer.com/cover-letter/34091): 실제 문항은 타인과 상호작용한 성공 또는 실패 사례와 배움을 묻는다. 다른 전공 팀원의 제안을 받아 주제를 바꾸고 역할을 나눈 흐름은, 협업에서 수용·분업을 답할 수 있음을 보여 준다.
- [ER10](../cases/expert-reviewed.md#er10--중소벤처기업진흥공단)은 5/5 평가에서 핵심가치 경험의 협업 과정과 공공기관 업무 맥락을 호평받았다. 협업의 질은 활동명보다 역할·조정 과정과의 연결로 판단한다.

### 의도와 하위 요구

독자는 공동 목표 안에서 맡은 역할, 타인과 정보를 어떻게 주고받았는지, 의견·일정·의존성을 어떻게 조율했는지, 팀 결과와 개인 기여가 어떻게 구분되는지 본다. 협업은 갈등이 없어도 성립한다. 의견 대립이 있어도 갈등의 이해관계·해결 원칙을 묻지 않는다면 협업 과정으로만 쓴다.

### 적합한 소재

- 역할이 나뉜 과제에서 인수인계, 일정 공유, 검토, 피드백 반영을 한 경험.
- 타인의 전문성·제안을 받아 계획 또는 산출물을 바꾼 경험.
- 팀 결과와 본인 기여·다른 사람의 기여를 구별해 설명할 수 있는 경험.

단독 수행 경험, 갈등 자체만 있고 공동 작업 방식이 없는 경험은 협업의 주 소재로 약하다.

### 전개 선택지

1. **역할 연결 중심:** 공동 목표 → 각 책임/의존성 → 내가 만든 공유·검토 방식 → 팀 결과와 내 기여.
2. **수용·조정 중심:** 서로 다른 관점/정보 → 상대 의견을 확인한 행동 → 함께 바꾼 결정 → 배운 협업 방식.

Q05 갈등과 같은 사건을 쓸 수는 있다. Q04에서는 일하는 방식을 개선한 협업 행동을 중심에, Q05에서는 충돌한 이해관계·중재 기준·설득 과정을 중심에 둔다. 하나를 다른 하나의 성공담으로 바꾸지 않는다.

### 작성·수정 절차

1. 공동 목표, 내 책임, 다른 구성원의 책임, 의존 관계를 분리해 적는다.
2. 내가 한 공유·질문·검토·조율 행동과 그 이유를 확인된 순서대로 배치한다.
3. 팀의 산출물은 팀 결과로, 내가 낸 제안·정리는 개인 기여로 표기한다.
4. “함께 노력해 성공했다”만 있으면 작업 방식과 본인 행동을 복원한다. 내 역할이나 결과가 빠졌다면 작업용 표식으로 남기며, 팀원의 행동을 본인 성과로 고치지 않는다.

### 피할 선택과 짧은 예시

팀명·수상만 쓰기, `우리`로 개인 행동을 지우기, 의견 차이만 적고 공동 작업의 변화를 빼기는 피한다.

`[가상 예시] 발표 자료와 데이터 정리의 마감이 맞물려 있어, 저는 각 파일의 완료 기준과 담당자를 공유 문서에 적었습니다. 팀원들이 갱신한 내용을 바탕으로 발표 순서를 조정했고, 최종 발표는 팀 공동 결과로 제출했습니다.`
