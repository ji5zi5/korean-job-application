# 작성 품질 비교 — 유지보수 전용

스킬을 수정하거나 성능 비교를 요청받았을 때만 쓴다. 지원자의 정상 자소서 작성·첨삭에서는 이 문서나 정답 기준을 불러오지 않는다. 아래 네 입력은 공개된 **합성 개발용 사례**이며, 비공개 평가 세트나 실제 합격자의 자료가 아니다.

## 실행과 판정

1. 바꾸기 전 스킬 폴더와 수정본을 각각 고정한다. 생성 모델·추론 설정·도구 권한·사용자 입력·분량 기준은 같게 한다. 각 요청은 별도 깨끗한 대화에서 실행하고, 작성 agent에는 사용자 입력과 해당 스킬 경로만 준다. 비교 목적, 기대 답안, 의심 결함, 다른 버전의 응답은 주지 않는다.
2. WQ02는 실제 두 번의 사용자 메시지로 실행한다. 첫 응답이 끝나기 전에 두 번째 답변을 알려 주거나 모델에게 다음 사용자 답을 만들어내게 하지 않는다. 원문 응답과 실제 읽은 참조·실행 설정·스킬 revision을 기록한다.
3. 버전·모델·생성 순서·파일 경로를 숨긴 응답 사본을 A/B로 제시한다. 쌍마다 배치를 바꾸고 키는 판정자 밖에 둔다. 원문이나 분량을 평가용으로 윤문하지 않는다. 판정자는 입력과 두 응답만 보고 아래 기준으로 근거를 남긴 뒤 버전 정보를 공개한다.
4. 먼저 허위 사실·역할/인과 확대·문항 미응답·출력 범위·분량 위반을 확인한다. 더 유창하다는 이유로 이 결함을 상쇄하지 않는다. 문제가 없는 답안끼리는 **질문에 답하는 중심 주장, 판단과 행동의 설명, 공고 과업과의 관련성, 사용자의 관점·어휘, 읽기 흐름**을 비교한다. 더 길거나 두괄식이라는 이유만으로 우수 판정을 주지 않는다.
5. 판정은 A 우세 / B 우세 / 동률 / 판정 불가 중 하나이며, 결정한 실제 대목과 이유를 적는다. 다회차 요청은 첫 질문과 최종 답안을 모두 판단한다. 단순 어휘 취향만으로 승자를 고르지 않는다. 별점·AI 유사성·합격 가능성 점수는 매기지 않는다.
6. 경계가 애매하면 순서를 뒤집어 다시 판단하거나 지원자·채용 실무자의 의견을 받는다. 모델만 판정했으면 **모델 비교**로 표시하고 사람 전문가 평가로 부르지 않는다. 의견이 갈리면 불확실성을 남긴다.
7. 드러난 결함의 원인이 있는 지침·예시만 수정한 뒤 영향받은 요청을 재실행한다. 좋은 부분도 사라졌는지 확인한다. 차이가 없으면 동률로 기록하며, 승리가 나올 때까지 생성하거나 유리한 응답만 고르지 않는다.

작은 개발용 비교는 개선 방향을 점검하는 수단이다. 전체 직무의 성능·모든 모델의 성능·합격 효과를 증명하지 않는다. 새로운 실패가 나타나면 기존 시연과 다른 이야기의 입력을 추가하고, 그 입력을 이용한 수정 뒤에는 미사용 사례로도 확인한다. 실제 지원자 자료를 수집·저장·공개하는 권한은 이 절차가 부여하지 않는다.

## 고정 입력

분량은 공백 포함 코드포인트 수, 문항별 본문만 계산한다. 공개 문항 원문이나 고용주 양식의 길이 규칙을 대체하지 않는다.

### WQ01 기술 직무 소재 선택과 완성 초안

**사용자 1차 메시지**

> 가상 새결서비스 QA 직무 공고는 오류 재현 조건 정리와 수정 전후 확인이야. 문항은 문제 해결 역량을 본인 역할과 결과 중심으로 설명하라는 거야. 후보 A: 해커톤에서 팀이 우수상을 받았고 나는 소개 자료를 만들었어. 후보 B: 동아리 검색 페이지에서 일부 상품명이 검색되지 않았어. 원본 목록에는 상품이 있는 걸 확인했고 저장된 이름 끝의 공백이 검색 입력과 다르다는 걸 찾았어. 나는 입력과 저장값의 앞뒤 공백을 제거해서 비교하자고 제안했어. 구현은 동료가 했고 나는 공백 있는 이름과 없는 이름 세 쌍으로 다시 확인했어. 수정 뒤 두 방식 모두 해당 상품을 찾았고 그 확인 항목을 팀 체크리스트에 남겼어. B에서는 원본에 상품이 있는데 검색에서만 빠져서 화면을 고치기 전에 비교 조건을 먼저 확인한 거야. 이 사실만으로 적합한 소재를 골라 500자 이내의 완성 답안을 써줘. 본문만.

### WQ02 선택 이유 인터뷰에서 초안까지

**사용자 1차 메시지**

> 문항은 협업 중 의견 차이를 어떻게 조율했는지야. 팀 보고서 마감 때 한 팀원은 바로 합치자고 했고 다른 팀원은 자료를 더 찾자고 했어. 나는 필수 자료와 추가 자료를 나눠 제출 순서를 정하자고 했고 팀은 그 순서로 보고서를 제출했어. 왜 그렇게 정했는지는 아직 설명 안 했네. 자소서 재료를 같이 정리해줘. 질문은 하나씩 해줘.

**사용자 2차 메시지**

> 공통 필수 자료는 이미 있었고 추가 자료는 결론을 바꾸는 내용이 아니었어. 그래서 제출할 부분을 먼저 확정하되, 추가 자료도 별도로 정리해서 버리지 않으려고 했어. 두 팀원에게 이 기준을 설명했고 둘 다 동의했어. 제출까지는 했고 평가 결과는 몰라. 이제 이 사실만으로 400자 이내 본문을 써줘.

### WQ03 판매 직무 근거와 사용자 말투 보존

**사용자 1차 메시지**

> 고객의 요구를 파악해 대응한 경험을 묻는 매장 판매직 자소서야. 전체를 다듬되 내 담백한 말투는 살려줘. 450자 이내, 수정본만 줘. 원문: 저는 설명을 잘하는 것보다 먼저 물어보는 편입니다. 매장에서 선물을 고르던 손님이 가격표만 번갈아 보고 있었습니다. 저는 누구에게 줄 선물인지와 들고 갈 거리를 물었습니다. 손님은 가족에게 줄 것이고 대중교통으로 두 시간 이동한다고 했습니다. 그래서 가격이 비슷한 두 제품의 무게와 포장 상태를 함께 보여드렸습니다. 손님은 가벼운 제품을 골랐고 포장이 편하다고 했습니다. 이후 같은 질문을 동료에게도 공유했습니다. 이는 탁월한 고객 중심 마인드와 뛰어난 영업력을 증명하는 혁신적 성과입니다. 추가 사실은 없고 매출 증가는 측정하지 않았습니다.

### WQ04 같은 경험의 서로 다른 직무 강조

**사용자 1차 메시지**

> 같은 경험으로 가상 A사 운영지원과 B사 고객상담의 자소서를 각각 써줘. 두 문항 모두 직무에 활용할 수 있는 경험을 묻고 각 350자 이내야. A 공고는 신청 기록의 오류 확인·담당자 전달, B 공고는 고객 문의 의도 파악·설명·인수인계를 제시해. 경험: 행사 신청자가 신청 상태를 반복해서 물었어. 나는 문의를 듣고 접수 완료와 승인 완료를 같은 뜻으로 이해하는 경우가 있다는 걸 확인했어. 신청 기록에서 두 상태를 따로 표시해 담당자와 대조했고, 신청자에게 접수와 승인의 차이를 설명했어. 같은 설명이 필요한 문의와 확인할 기록을 인수인계 메모에 남겼고 다음 근무자가 그 메모를 사용했어. 이 사실 외에 성과 수치는 없어. 제목은 A사/B사만 쓰고 각 본문을 줘.

## 관찰 기준

| 요청 | 확인할 실제 동작 | 감점 사유가 아닌 것 |
| --- | --- | --- |
| WQ01 | 질문에 맞는 경험을 선택하고 관찰·선택 이유·제안·동료 구현·본인 확인·결과의 관계를 보존한다. | 수상 경험 미사용, 개선율 미기재 |
| WQ02 | 미제공 판단 이유를 중립적으로 한 주제씩 확인하고, 추가 답변 뒤에는 완성 본문으로 전환한다. | 평가 결과를 모르므로 수상·호평을 쓰지 않은 것 |
| WQ03 | 고유한 관점과 구체 질문·대응·고객 반응·동료 공유는 살리고 과장을 덜어낸다. | 모든 문장을 새롭게 쓰지 않은 것, 매출 수치 미기재 |
| WQ04 | 같은 사실의 역할·결과는 고정하고 공고별 중심 행동과 설명 순서를 달리한다. | 같은 경험 재사용, 회사 찬양·미확인 전략 미기재 |

## 기록 양식

- 실행일, 원본/수정본 revision, 생성 모델·설정, 입력 ID, 실제 응답 경로
- 사실·문항·분량/출력범위: 통과 또는 구체적 위반
- 숨긴 A/B의 판단과 근거, 판정자 유형(사람/모델), 공개한 버전 키
- 바꿀 지침 또는 유지할 동작, 재실행 결과, 표본·재사용·판정의 한계

기존 [문자 수 검사](test_count_chars.py)는 계산 도구의 회귀 검사다. 이 작성 품질 비교를 대체하지 않으며, 이 문서의 문구 존재를 검사하는 코드로 작성 품질 통과를 주장하지 않는다.
